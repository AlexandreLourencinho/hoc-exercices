# User Package – Level 1 Exercise

The **user package** introduces **business logic complexity**.

Unlike the `product` package:

* the **controller is already implemented**
* the **service must be fully implemented**
* the **mapper must be completed**
* the **repository is already functional**
* **unit tests exist** and must pass

This package focuses on:

* business rules
* validation
* exception handling
* correct interaction between service, repository and mapper

---

## General rules for this package

### The architecture is already defined

Entities, DTOs, exceptions and repository are already implemented.

You are **not asked to design the project**,
you are asked to **implement business rules correctly**.

Before coding, carefully analyze:

* the entity
* the DTOs
* the controller
* the service interface
* the exceptions

Together, they define the expected behavior.

---

## Controller

The **user controller is already implemented** and must **not be modified**.

It is intentionally left exactly as in the solution so that you have:

* one full example of a controller
* an example of endpoint definitions
* an example of try / catch handling

⚠️ You may notice warnings regarding `ResponseEntity` without generics.
This is **intentional** and part of the first level of complexity.

---

### Important: respect controller behavior

The controller already contains:

* mappings
* parameters (path params, request params, body)
* try / catch blocks

Your service **must respect this behavior**:

* throw the expected exceptions
* let the controller handle them

Do **not** change controller logic to compensate for service errors.

---

### Endpoint base path

All user endpoints are available under:

```
localhost:8080/user
```

Depending on the endpoint:

* some use path parameters
* some use request parameters
* some use a request body

They are differentiated by:

* HTTP method (`GET`, `POST`, `PUT`, `DELETE`)
* method parameters

---

## DTO package

DTOs represent the objects:

* received from the frontend / Postman
* returned to the frontend / Postman

They must not expose all entity fields.

---

### `UserDTOCreate`

Sent by the request to create a new user.

---

### `UserDTOGet`

Returned by the backend to provide user information.

Sensitive data (like passwords) must **never** be returned.

---

### `UserDTOLogin`

Sent by a user to log in.

⚠️ A user can log in using:

* their username
* or their email

You must manage both cases in the service.

---

### `UserDTOUpdate`

Sent by the request to update an existing user.

---

## Entity package

The `UserEntity` represents the `user` table in the database.

Persistence annotations are already defined and documented in the code.

You are expected to:

* understand what each annotation does
* respect the constraints defined by the entity

---

### Important constraints in the entity

* `id`

    * primary key
    * auto-incremented
    * generated by JPA
* `username`

    * must be unique
* `email`

    * must be unique
* `(name, firstname)`

    * unique **together** (composite unique constraint)

These constraints must be enforced at the **business level** (so, in the service), not only by the database.

---

## Exception package

The user package defines several business exceptions.

Each one exists for a reason and must be thrown when appropriate.

### Available exceptions

* `UserNotFoundException`
* `InvalidCredentialException`
* `EmailAlreadyExistsException`
* `UsernameAlreadyTakenException`
* `NameAndFirstnameAlreadyExistsException`

The service is responsible for throwing these exceptions.
The controller already knows how to handle them.

---

## Mapper package

The mapper is responsible for converting:

* DTOs → Entities
* Entities → DTOs

One method is already implemented as an example.

---

### Implemented method (example)

#### `getEntityFromDTOCreate`

Already implemented.

It:

* creates a new `UserEntity`
* sets the ID to `null`
* hashes the password using the provided `PasswordManager`

This method serves as a **reference for expected mapping style**.

---

### Methods to implement

#### `getDTOGetFromEntity`

Should return a `UserDTOGet` from a `UserEntity`.

Only fields intended to be exposed must be mapped.

---

#### `updateEntityFromDTO`

Updates an existing entity using a `UserDTOUpdate`.

Rules:

* retrieve the existing entity first
* update its fields
* do **not** change the ID
* password handling must be correct if applicable

---

## Repository package

The user repository is already implemented and functional.

It extends `JpaRepository` and contains several `findBy...` methods.

Important reminders:

* every `findBy...` method returning a single result returns an `Optional`
* method names follow standard JPA naming conventions

You are expected to:

* use these methods correctly in the service
* handle empty results properly

---

## Service package

The **user service is the core of this package**.

The interface already defines all required methods.
Your job is to **implement them correctly**.

The service must:

* enforce business rules
* validate data
* throw appropriate exceptions

---

### Service methods

#### `loginUser`

Authenticates a user.

Rules:

* login can be done using **email or username**
* password must be verified using `PasswordManager`
* invalid credentials must trigger `InvalidCredentialException`

Returns user information if successful.

---

#### `getUser`

Returns information for a single user.

If the user does not exist, throw `UserNotFoundException`.

---

#### `getUserEntity`

Must be left **unchanged**.

This is a business method used by the `order` package.

---

#### `getUsers`

Returns a list of all users.

---

#### `getSetOfUsers`

Returns a set of users based on a list of user IDs.

---

#### `saveUser`

Creates and saves a new user.

Before saving, you must:

* check for duplicate username
* check for duplicate email
* check for duplicate `(name, firstname)`

If a rule is violated, throw the corresponding exception.

Returns the created user as a DTO.

---

#### `updateUser`

Updates an existing user.

Rules:

* retrieve the existing entity first
* update its fields
* save the entity
* return the updated DTO

⚠️ Duplicate checks must **exclude the user being updated**.

Example:
If the user already has `"aaa"` as username and the update does not change it, this is valid.

---

#### `deleteUser`

Deletes a single user.

If the user does not exist, throw `UserNotFoundException`.

---

#### `deleteUsers`

Deletes multiple users.

---

#### `checkDuplicateFields`

Two different methods are expected:

* one for creation
* one for update

These methods must check:

* username uniqueness
* email uniqueness
* `(name, firstname)` uniqueness

When updating, the current user must not be considered a duplicate of itself.

---

## PasswordManager utility

A password utility is provided and must be used.

It:

* hashes passwords using SHA-512
* verifies passwords by comparing hashes

⚠️ This implementation is intentionally simple and **not production-ready**.

The goal is to:

* avoid introducing Spring Security complexity
* focus on business logic instead of authentication configuration

---

## Final note

This package represents a **significant increase in complexity** compared to `product`.

Take your time to:

* read existing code
* understand the contracts
* reason about business rules

This package prepares you for the final step: **the order package**,
where everything will have to be implemented from scratch.
